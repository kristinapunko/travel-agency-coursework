# Веб-сайт автоматизації управління роботою турагентства

Вебзастосунок для автоматизації підбору, перегляду та онлайн-бронювання туристичних послуг (Тема №33).

**Поточний стан:** реалізовано багаторівневу клієнтську маршрутизацію (SPA), повний локальний CRUD-сценарій керування заявками з валідацією форм, синхронізацію фільтрів із URL та оброблення станів відсутності даних.

---

* **Docker Compose:** v2.x

## Запуск

### Нативний запуск

Встановлення залежностей:

```bash
npm install
```

Запуск середовища розробки:

```bash
npm run dev
```

Після запуску застосунок доступний за адресою:

`http://localhost:5173`

### Запуск у Docker

Побудова Docker-образу:

```bash
docker compose build
```

Одноразове встановлення залежностей у виділений volume:

```bash
docker compose run --rm web npm install
```

Запуск середовища розробки:

```bash
docker compose up
```

Застосунок доступний за адресою:

`http://localhost:5173`

Зупинення середовища:

```bash
docker compose down
```

або `Ctrl + C` у терміналі, де виконується `docker compose up`.

# Лабораторна робота 2.2

## Клієнтська маршрутизація та навігація

### Маршрутизація та залежності

Для реалізації клієнтської маршрутизації використовується бібліотека `react-router` версії `^7.18.4`.

Застосовано декларативний підхід із використанням:

* `BrowserRouter`;
* `Routes`;
* `Route`;
* `Outlet`;
* `NavLink`;
* `useSearchParams`.

Основна структура застосунку побудована навколо єдиного кореневого макета `AppLayout`, який містить спільну навігацію та точку монтування дочірніх сторінок через `Outlet`.

Для розділу заявок використовується вкладений макет `BookingsLayout`.

Головна навігація реалізована за допомогою `NavLink` із підсвічуванням активного пункту та використанням `aria-current="page"` для покращення доступності.

### Маршрути для перевірки

| Маршрут                       | Призначення                                    |
| ----------------------------- | ---------------------------------------------- |
| `/`                           | Головна сторінка із вітальним блоком           |
| `/tours`                      | Каталог усіх турів                             |
| `/tours?q=фьорди&available=1` | Каталог із фільтрами, синхронізованими з URL   |
| `/tours/1`                    | Детальна інформація про конкретний тур         |
| `/tours/unknown-999`          | Перевірка оброблення неіснуючого туру          |
| `/bookings`                   | Список заявок                                  |
| `/bookings/new`               | Створення заявки без попередньо вибраного туру |
| `/bookings/new?tourId=1`      | Створення заявки для конкретного туру          |
| `/bookings/book-001/edit`     | Редагування демонстраційної заявки             |
| `/non-existent-page`          | Оброблення невідомого маршруту (404)           |

# Лабораторна робота 3.1

## Розроблення форм, валідації та операцій опрацювання даних

### Архітектура даних та CRUD-контракт

Власником колекції заявок є `BookingsProvider`, реалізований на основі `React Context` та `useState`. Провайдер розташований у спільній оболонці `AppLayout`, тому стан заявок є доступним для списку, сторінок деталей та форм створення й редагування.

Початкові дані завантажуються з:

```text
src/data/bookings.js
```

Основні CRUD-операції:

* **`createBooking(input)`** — виконує валідацію даних, генерує унікальний ідентифікатор за допомогою `crypto.randomUUID()` та додає новий запис до колекції.
* **`updateBooking(id, input)`** — перевіряє введені дані та замінює відповідний запис за допомогою `.map()`.
* **`deleteBooking(id)`** — видаляє заявку з колекції за допомогою `.filter()`.

Усі операції виконуються незмінно, без прямої модифікації попереднього стану.

### Повідомлення про результати операцій

Для інформування користувача реалізовано компонент `BookingNotice` із семантичною роллю `role="status"`.

Повідомлення про успішне виконання операцій зберігаються під час переходу між сторінками, тому користувач отримує зворотний зв'язок навіть після навігації.

### Захист від випадкового видалення

Видалення заявки потребує підтвердження через `window.confirm`.

У діалоговому вікні відображаються номер заявки та назва відповідного туру.

Логіка підтвердження винесена в окремий хук `useDeleteBooking`.

## Валідація форми

Правила предметної області реалізовано в окремому модулі:

```text
src/domain/bookingValidation.js
```

Валідація виконується єдиною чистою функцією без використання сторонніх бібліотек для роботи з формами.

### Правила перевірки

* **`customerName`** — обов'язкове поле довжиною від 3 до 60 символів після видалення зайвих пробілів.
* **`customerPhone`** — номер телефону українського формату, що містить від 10 до 13 цифр і перевіряється регулярним виразом.
* **`customerEmail`** — обов'язкова адреса електронної пошти з перевіркою коректності формату.
* **`travelersCount`** — кількість туристів від 1 до 10. У чернетці форми значення зберігається як текст, що забезпечує коректне введення даних.
* **`needsTransfer`** — булеве поле, яке визначає необхідність трансферу.
* **`notes`** — необов'язкове поле для додаткових приміток.
* **Залежне правило:** якщо кількість туристів перевищує 4, трансфер стає обов'язковим.

### Доступність форми

Для полів форми реалізовано:

* `aria-invalid` для позначення некоректних значень;
* `aria-describedby` для зв'язування полів із підказками та повідомленнями про помилки;
* автоматичне переведення фокуса на перше некоректне поле після невдалої спроби подання форми;
* єдину систему повідомлень про помилки українською мовою.

Використання `noValidate` дозволяє вимкнути стандартні браузерні повідомлення та застосувати єдину логіку валідації застосунку.

## Пошук, фільтрація та сортування заявок

На сторінці `/bookings` реалізовано пошук, фільтрацію та сортування заявок.

Стан фільтрів синхронізується з адресним рядком браузера за допомогою `useBookingFilters`.

### Параметри URL

* **`q`** — пошук за назвою туру, ім'ям клієнта, номером телефону та примітками без урахування регістру.
* **`transfer`** — фільтрація за наявністю трансферу: `all`, `yes`, `no`.
* **`sort`** — сортування за туром, клієнтом або кількістю туристів за зростанням чи спаданням.

Оновлення параметрів пошуку виконується з `{ replace: true }`, тому зміна фільтрів не створює зайвих записів у історії браузера.

### Оброблення відсутності даних

Передбачено два різні стани:

1. **Колекція заявок порожня** — користувачу відображається повідомлення про відсутність заявок із пропозицією перейти до каталогу.
2. **Заявки існують, але поточні фільтри не дали результатів** — відображається повідомлення про відсутність збігів та кнопка скидання фільтрів.

## Межі збереження даних

> **Важливе обмеження поточної версії:** дані заявок зберігаються виключно в оперативній пам'яті браузера в межах поточного сеансу.

Створені, змінені та видалені заявки зберігаються під час переходів між сторінками застосунку.

Після повного перезавантаження сторінки (`F5`) стан повертається до початкових демонстраційних записів із:

```text
src/data/bookings.js
```

Незбережена чернетка форми скидається після виходу зі сторінки. Для запобігання випадковій втраті введених даних реалізовано перевірку `isDirty` та підтвердження через `window.confirm`.

Підключення постійного сховища або асинхронного бекенду — REST API / `localStorage` — передбачено на наступних етапах розроблення (Лабораторна робота 3.2).

## Обмеження поточної версії

Поточна реалізація використовує локальний стан React без постійного сховища.

Тому:

* дані не синхронізуються між різними вкладками;
* після `F5` створені під час сеансу записи повертаються до початкового стану;
* відсутній постійний серверний бекенд;
* відсутня синхронізація з базою даних.

Ці обмеження є свідомими та відповідають поточному етапу розроблення.
