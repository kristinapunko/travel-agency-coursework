# План проєкту: Веб-сайт автоматизації управління роботою турагентства

## 1. Тема та проблема предметної області

**Тема проєкту:**
**«Веб-сайт автоматизації управління роботою турагентства» (Тема №33).**

### Актуальність проєкту

Сучасний туристичний бізнес потребує швидкого та зручного обслуговування клієнтів. Традиційний процес підбору туру часто передбачає тривале листування або телефонні розмови з менеджером турагентства. Клієнту необхідно уточнювати актуальні пропозиції, ціни, наявність місць, умови поїздки та лише після цього оформлювати заявку.

Такий підхід має низку недоліків:

* значні витрати часу на комунікацію між клієнтом і менеджером;
* збільшення навантаження на працівників турагентства;
* ризик втрати потенційних клієнтів через тривале очікування відповіді;
* складність оперативного контролю актуальних заявок;
* необхідність ручного опрацювання великої кількості однотипних запитів.

### Запропоноване рішення

Для вирішення зазначених проблем розробляється **вебзастосунок для автоматизації роботи турагентства**.

Система дозволяє користувачам переглядати доступні туристичні пропозиції, ознайомлюватися з їх характеристиками, виконувати пошук і фільтрацію, обирати потрібний тур та оформлювати заявку на бронювання через керовану форму з валідацією введених даних.

Для працівників турагентства система забезпечує локальне опрацювання заявок за CRUD-сценарієм: створення, перегляд деталей, редагування та вилучення з підтвердженням. Також реалізовано пошук за даними заявки, фільтрацію за необхідністю трансферу та сортування за різними критеріями.

## 2. Сутності предметної області

Основними сутностями системи є **тури, бронювання (заявки) та відгуки**.

### 2.1. Тур (`Tour`)

Сутність **Tour** представляє туристичну пропозицію, доступну в каталозі. На поточному етапі каталог турів є незмінним довідником.

| Поле          | Тип              | Опис                                                |
| ------------- | ---------------- | --------------------------------------------------- |
| `id`          | `string`         | Унікальний стабільний ідентифікатор туру            |
| `name`        | `string`         | Назва туристичної програми                          |
| `country`     | `string`         | Країна або основний географічний напрямок           |
| `duration`    | `string`         | Загальна тривалість подорожі                        |
| `price`       | `number`         | Поточна вартість туру в гривнях                     |
| `oldPrice`    | `number \| null` | Попередня вартість для акційних турів або `null`    |
| `description` | `string`         | Стислий опис екскурсійної чи відпочинкової програми |
| `date`        | `string`         | Період проведення туру                              |
| `transport`   | `string`         | Спосіб подорожі та місто відправлення               |
| `food`        | `string`         | Тип харчування                                      |
| `travelers`   | `string`         | Базовий розрахунок на кількість осіб                |
| `rating`      | `number`         | Середня оцінка туру за відгуками                    |
| `reviews`     | `number`         | Загальна кількість відгуків                         |
| `isAvailable` | `boolean`        | Стан наявності вільних місць                        |
| `imageUrl`    | `string`         | Посилання на зображення для картки туру             |

### 2.2. Бронювання / Заявка (`Booking`)

Сутність **Booking** представляє заявку клієнта на бронювання туру та є основною динамічною сутністю локального CRUD-циклу.

| Атрибут          | Тип       | Правило валідації та обмеження                                  |
| ---------------- | --------- | --------------------------------------------------------------- |
| `id`             | `string`  | Унікальний ідентифікатор, автоматично генерується при створенні |
| `tourId`         | `string`  | Посилання на тур із каталогу                                    |
| `customerName`   | `string`  | Обов'язкове поле, від 3 до 60 символів після `trim()`           |
| `customerPhone`  | `string`  | Номер українського формату, 10–13 цифр                          |
| `customerEmail`  | `string`  | Обов'язкова коректна адреса електронної пошти                   |
| `travelersCount` | `number`  | Ціле число від 1 до 10                                          |
| `needsTransfer`  | `boolean` | Ознака необхідності трансферу                                   |
| `notes`          | `string`  | Додаткові побажання клієнта, необов'язкове поле до 300 символів |

**Залежне правило:** якщо `travelersCount > 4`, поле `needsTransfer` повинно мати значення `true`.

### 2.3. Відгук (`Review`)

Сутність **Review** передбачена для збереження оцінок і коментарів клієнтів після подорожі. Реалізація цієї сутності запланована на наступних етапах інтеграції з API.

| Атрибут   | Тип      | Опис                                        |
| --------- | -------- | ------------------------------------------- |
| `id`      | `string` | Унікальний ідентифікатор відгуку            |
| `tourId`  | `string` | Ідентифікатор туру, якого стосується відгук |
| `author`  | `string` | Автор відгуку                               |
| `rating`  | `number` | Оцінка від 1 до 5                           |
| `comment` | `string` | Текстове враження клієнта                   |

## 5. Структура сторінок, маршрутизація та оброблення станів

Усі основні маршрути застосунку обгорнуті в кореневий макет `AppLayout`, який містить спільну навігацію та дочірню точку монтування `Outlet`.

| Адреса                      | Компонент сторінки                  | Параметри               | Джерело даних                              | Поведінка за відсутності запису / помилці                    |
| --------------------------- | ----------------------------------- | ----------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| `/`                         | `HomePage`                          | —                       | Статичний контент                          | Сторінка відображається завжди                               |
| `/tours`                    | `CatalogContainer` → `TourListPage` | `q`, `available`        | Масив `tours`                              | `EmptyState`                                                 |
| `/tours/:tourId`            | `TourDetailsPage`                   | `tourId`                | `tours.find(id)`                           | `NotFoundPage`                                               |
| `/bookings`                 | `BookingsPage`                      | `q`, `transfer`, `sort` | `BookingsProvider`                         | «Заявок ще немає» або «За фільтрами нічого не знайдено»      |
| `/bookings/new`             | `BookingCreatePage`                 | `tourId`                | `tours.find(tourId)`                       | Без параметра — вибір туру; неправильний ID — `NotFoundPage` |
| `/bookings/:bookingId`      | `BookingDetailsPage`                | `bookingId`             | `bookings.find(id)` → `tours.find(tourId)` | `NotFoundPage`                                               |
| `/bookings/:bookingId/edit` | `BookingEditPage`                   | `bookingId`             | `bookings.find(id)` → `tours.find(tourId)` | `NotFoundPage`                                               |
| `*`                         | `NotFoundPage`                      | —                       | —                                          | Глобальне оброблення маршруту 404                            |

### Правила маршрутизації та оброблення даних

1. **Параметри шляху** (`:tourId`, `:bookingId`) використовуються для точної ідентифікації конкретного об'єкта.

2. **Query-параметри** використовуються для передачі стану пошуку, фільтрації та вибору:

   * у каталозі — `q` та `available`;
   * у списку заявок — `q`, `transfer`, `sort`;
   * при створенні заявки — `tourId`.

3. **Перехід після створення або редагування:** після успішного збереження заявки виконується програмна навігація на сторінку перегляду відповідного запису:

```js
navigate(`/bookings/${encodeURIComponent(result.record.id)}`, {
  replace: true,
});
```

4. **Перехід після видалення:** після підтвердженого видалення користувач повертається до `/bookings`, де відображається системне повідомлення з `role="status"`.

5. **Захист від втрати даних:** якщо форма містить незбережені зміни (`isDirty`), вихід зі сторінки або скидання форми потребує додаткового підтвердження через `window.confirm`.

6. **Межі збереження:** дані заявок зберігаються в пам'яті клієнта за допомогою `React Context`. Вони доступні між сторінками протягом поточного сеансу, але після повного перезавантаження сторінки (`F5`) стан повертається до початкових демонстраційних даних.

## 6. Архітектура стану та CRUD

Централізоване керування заявками реалізовано через `BookingsProvider`, побудований на основі `React Context` та `useState`.

Провайдер розміщується у спільній оболонці застосунку, завдяки чому одна колекція заявок використовується на сторінках списку, деталей, створення та редагування.

### Основні операції

* **`createBooking(input)`** — перевірка даних, генерація ідентифікатора та додавання нової заявки.
* **`updateBooking(id, input)`** — перевірка даних та оновлення відповідного запису.
* **`deleteBooking(id)`** — вилучення заявки з колекції.

Операції виконуються незмінно, без прямої модифікації попереднього стану.

## 7. Валідація та доступність

Правила валідації заявки реалізовано в окремому модулі:

```text
src/domain/bookingValidation.js
```

Валідація виконується централізовано та не залежить від UI-компонентів.

Для забезпечення доступності форми використовуються:

* `aria-invalid`;
* `aria-describedby`;
* семантичні повідомлення про помилки;
* автоматичне переведення фокуса на перше некоректне поле;
* `noValidate` для використання єдиної системи валідації застосунку.

## 8. Пошук, фільтрація та сортування заявок

Для сторінки `/bookings` реалізовано окремий хук `useBookingFilters`, який синхронізує стан фільтрів з URL.

Доступні параметри:

* **`q`** — пошук за назвою туру, ім'ям клієнта, номером телефону та примітками;
* **`transfer`** — фільтрація за трансфером: `all`, `yes`, `no`;
* **`sort`** — сортування за туром, клієнтом або кількістю туристів за зростанням / спаданням.

Оновлення параметрів пошуку виконується із `{ replace: true }`, що запобігає створенню зайвих записів в історії браузера.

Для відсутності результатів передбачено два окремі стани:

* **порожня колекція** — у системі ще немає заявок;
* **порожній результат фільтрації** — заявки існують, але не відповідають поточним критеріям.

---

## 9. Межі поточного етапу

На етапі Л 3.1 дані заявок зберігаються лише в оперативній пам'яті браузера.

Поточна реалізація забезпечує:

* спільний стан заявок між сторінками;
* повний локальний CRUD-цикл;
* валідацію даних;
* пошук, фільтрацію та сортування;
* оброблення порожніх станів;
* захист від випадкової втрати незбережених змін.

Водночас після повного перезавантаження сторінки стан повертається до початкових даних із `src/data/bookings.js`.

Постійне збереження даних та асинхронна взаємодія з сервером плануються на етапі **Л 3.2**.

## 10. Подальші етапи розроблення

### Лабораторна робота 3.2

Передбачається:

* інтеграція з асинхронним джерелом даних;
* використання REST API / Fetch;
* оброблення станів завантаження;
* оброблення помилок мережевих запитів;
* синхронізація даних із серверною частиною.

### Лабораторна робота 4.1 / курсова робота

Передбачається:

* комплексне тестування функціональності;
* перевірка основних користувацьких сценаріїв;
* фінальне покращення доступності;
* інтеграція всіх розроблених модулів;
* підготовка документації;
* підготовка та проведення захисту курсового проєкту.
