# Архітектура компонентів застосунку «Веб-сайт автоматизації управління роботою турагентства» — ЛР 1.2

> **Мета роботи:** виконати рефакторинг монолітної структури застосунку з ЛР 1.1 та перейти до модульної компонентної архітектури з чітким розмежуванням відповідальностей.

---

## 1. Опис архітектури

У результаті рефакторингу застосунок **Веб-сайт автоматизації управління роботою турагентства** було розділено на окремі функціональні та UI-компоненти.

Архітектура побудована за принципом **композиції компонентів** та передбачає розподіл за предметними областями:

* `layout` — загальна структура сторінки;
* `navigation` — навігація застосунку;
* `tours` — компоненти каталогу турів;
* `bookings` — компоненти, пов'язані із заявками;
* `ui` — універсальні UI-компоненти;
* `pages` — компоненти окремих сторінок;
* `data` — дані каталогу турів.

Такий підхід зменшує зв'язаність компонентів, спрощує повторне використання коду та створює основу для подальшого масштабування застосунку.

## 3. Композиційне дерево

Застосунок наразі працює як **одна HTML-сторінка без маршрутизатора**. Навігація між основними розділами виконується за допомогою якірних посилань:

* `#about` — інформація про компанію;
* `#catalog` — каталог турів;
* `#booking` — форма заявки.

Структура композиції компонентів має такий вигляд:

```text
App
└── AppLayout (title, links)
    ├── Header (title, links)
    │   └── MainNav (links)
    │
    ├── main#main-content
    │   ├── HomePage
    │   │   ├── Section (id="about", title)
    │   │   │
    │   │   └── Section (id="catalog", title)
    │   │       ├── CatalogSummary (total)
    │   │       └── TourList (items)
    │   │           ├── TourCard (key={tour.id}, tour)
    │   │           │   └── AvailabilityBadge (available)
    │   │           │
    │   │           └── EmptyState
    │   │               └── якщо items.length === 0
    │   │
    │   └── BookingPage (selectedTour)
    │       └── Section (id="booking", title)
    │           ├── AvailabilityBadge (available)
    │           ├── BookingFormPreview (idPrefix, tourName)
    │           │   ├── FormField (id, label, hint)
    │           │   └── AppButton (type, variant, disabled)
    │           │
    │           └── EmptyState
    │               └── якщо тур не передано
    │
    └── Footer (appTitle)
```

## 5. Основні архітектурні рішення

### 5.1. Композиція замість жорсткого зв'язування

Компоненти `AppLayout`, `Section` та `FormField` використовують властивість `children`.

Завдяки цьому вони **не залежать від конкретної структури переданого вмісту** та можуть повторно використовуватися в різних частинах застосунку.

Наприклад, один і той самий `Section` може використовуватися для:

* опису туристичної агенції;
* каталогу турів;
* форми бронювання.

Це дозволяє уникнути дублювання HTML-структури та логіки доступності.

---

### 5.2. Централізація правила доступності туру

Предметне правило відображення доступності винесено в окремий компонент:

```text
AvailabilityBadge
```

Компонент отримує просте булеве значення:

```jsx
<AvailabilityBadge available={tour.available} />
```

і самостійно визначає необхідний текст та CSS-клас.

Таким чином, однакова логіка використовується у різних частинах застосунку:

```text
TourCard
   │
   └── AvailabilityBadge

BookingPage
   │
   └── AvailabilityBadge
```

Це усуває дублювання та гарантує однакове відображення статусу доступності.

---

### 5.3. Розділення компонентів за доменами

Компоненти організовано відповідно до їхньої відповідальності:

```text
tours      → каталог та інформація про тури
bookings   → бронювання
layout     → структура сторінки
navigation → навігація
ui         → універсальні елементи інтерфейсу
pages      → сторінки застосунку
```

Таке розділення дозволяє швидко знаходити потрібний компонент і спрощує його подальше розширення.

---

### 5.4. Повторне використання UI-компонентів

Універсальні компоненти винесено до `components/ui`.

До них належать:

* `AppButton`;
* `EmptyState`;
* `FormField`;
* `Section`.

Вони не містять специфічної логіки туристичного каталогу та можуть використовуватися в інших частинах застосунку.

Наприклад, `EmptyState` може бути використаний як для порожнього каталогу:

```jsx
<EmptyState title="Турів не знайдено" />
```

так і для ситуації, коли не вибрано тур для бронювання.

## 6. Доступність

При проєктуванні компонентів враховано базові вимоги **Web Accessibility (a11y)**.

### Реалізовані механізми

* доступне навігаційне меню через `aria-label`;
* зв'язування секцій із заголовками через `aria-labelledby`;
* наявність `.skip-link` для швидкого переходу до основного контенту;
* єдиний семантичний `<main id="main-content">`;
* правильне зв'язування `label` та `input` через `for` / `id`;
* використання `aria-describedby` для додаткових підказок;
* безпечне значення `type="button"` для кнопки за замовчуванням.

Таким чином, структура компонентів враховує не лише візуальне відображення, а й семантику HTML та доступність інтерфейсу.

## 7. Форма бронювання

`BookingFormPreview` є демонстраційним компонентом форми.

Він **не виконує фактичне надсилання даних**. Подія `submit` блокується за допомогою:

```jsx
e.preventDefault()
```

Для уникнення конфліктів `id` між полями використовується властивість:

```text
idPrefix
```

Наприклад:

```text
booking-name
booking-email
```

Це дозволяє безпечно розміщувати декілька екземплярів форми на одній сторінці.

---

## 8. Переваги запропонованої архітектури

Запропонована компонентна структура забезпечує:

* **модульність** — кожен компонент має чітку відповідальність;
* **повторне використання** — універсальні компоненти можуть застосовуватися в різних частинах UI;
* **низьку зв'язаність** — компоненти взаємодіють переважно через `props`;
* **зменшення дублювання** — спільна логіка винесена в окремі компоненти;
* **підтримуваність** — зміни в одному компоненті не потребують редагування всієї сторінки;
* **масштабованість** — структура готова до подальшого розширення функціональності;
* **доступність** — компоненти містять необхідні семантичні та ARIA-атрибути.

## 9. Перспективи подальшого розвитку

Поточна архітектура створює основу для наступних етапів розвитку застосунку.

У майбутньому можливе:

1. підключення **React Router** для повноцінної маршрутизації;
2. використання **Redux Toolkit** для глобального стану;
3. винесення роботи з API в окремий шар;
4. додавання реального механізму бронювання;
5. розширення моделі `Tour`;
6. додавання фільтрації та сортування каталогу;
7. створення додаткових сторінок та функціональних модулів.
