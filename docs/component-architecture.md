# Архітектура компонентів застосунку «Веб-сайт автоматизації управління роботою турагентства» — ЛР 1.2

> **Мета роботи:** виконати рефакторинг монолітної структури застосунку з ЛР 1.1 та перейти до модульної компонентної архітектури з чітким розмежуванням відповідальностей.

---

## 1. Опис архітектури

У результаті рефакторингу застосунок **Веб-сайт автоматизації управління роботою турагентства** було розділено на окремі функціональні та UI-компоненти.

Архітектура побудована за принципом **композиції компонентів** та передбачає розподіл за предметними областями:

* `layout` — загальна структура сторінки;
* `navigation` — навігація застосунку;
* `tours` — компоненти каталогу турів;
* `bookings` — компоненти, пов'язані із заявками;
* `ui` — універсальні UI-компоненти;
* `pages` — компоненти окремих сторінок;
* `data` — дані каталогу турів.

Такий підхід зменшує зв'язаність компонентів, спрощує повторне використання коду та створює основу для подальшого масштабування застосунку.

## 3. Композиційне дерево

Застосунок наразі працює як **одна HTML-сторінка без маршрутизатора**. Навігація між основними розділами виконується за допомогою якірних посилань:

* `#about` — інформація про компанію;
* `#catalog` — каталог турів;
* `#booking` — форма заявки.

Структура композиції компонентів має такий вигляд:

```text
App
└── AppLayout (title, links)
    ├── Header (title, links)
    │   └── MainNav (links)
    │
    ├── main#main-content
    │   ├── HomePage
    │   │   ├── Section (id="about", title)
    │   │   │
    │   │   └── Section (id="catalog", title)
    │   │       ├── CatalogSummary (total)
    │   │       └── TourList (items)
    │   │           ├── TourCard (key={tour.id}, tour)
    │   │           │   └── AvailabilityBadge (available)
    │   │           │
    │   │           └── EmptyState
    │   │               └── якщо items.length === 0
    │   │
    │   └── BookingPage (selectedTour)
    │       └── Section (id="booking", title)
    │           ├── AvailabilityBadge (available)
    │           ├── BookingFormPreview (idPrefix, tourName)
    │           │   ├── FormField (id, label, hint)
    │           │   └── AppButton (type, variant, disabled)
    │           │
    │           └── EmptyState
    │               └── якщо тур не передано
    │
    └── Footer (appTitle)
```

## 5. Основні архітектурні рішення

### 5.1. Композиція замість жорсткого зв'язування

Компоненти `AppLayout`, `Section` та `FormField` використовують властивість `children`.

Завдяки цьому вони **не залежать від конкретної структури переданого вмісту** та можуть повторно використовуватися в різних частинах застосунку.

Наприклад, один і той самий `Section` може використовуватися для:

* опису туристичної агенції;
* каталогу турів;
* форми бронювання.

Це дозволяє уникнути дублювання HTML-структури та логіки доступності.

---

### 5.2. Централізація правила доступності туру

Предметне правило відображення доступності винесено в окремий компонент:

```text
AvailabilityBadge
```

Компонент отримує просте булеве значення:

```jsx
<AvailabilityBadge available={tour.available} />
```

і самостійно визначає необхідний текст та CSS-клас.

Таким чином, однакова логіка використовується у різних частинах застосунку:

```text
TourCard
   │
   └── AvailabilityBadge

BookingPage
   │
   └── AvailabilityBadge
```

Це усуває дублювання та гарантує однакове відображення статусу доступності.

---

### 5.3. Розділення компонентів за доменами

Компоненти організовано відповідно до їхньої відповідальності:

```text
tours      → каталог та інформація про тури
bookings   → бронювання
layout     → структура сторінки
navigation → навігація
ui         → універсальні елементи інтерфейсу
pages      → сторінки застосунку
```

Таке розділення дозволяє швидко знаходити потрібний компонент і спрощує його подальше розширення.

---

### 5.4. Повторне використання UI-компонентів

Універсальні компоненти винесено до `components/ui`.

До них належать:

* `AppButton`;
* `EmptyState`;
* `FormField`;
* `Section`.

Вони не містять специфічної логіки туристичного каталогу та можуть використовуватися в інших частинах застосунку.

Наприклад, `EmptyState` може бути використаний як для порожнього каталогу:

```jsx
<EmptyState title="Турів не знайдено" />
```

так і для ситуації, коли не вибрано тур для бронювання.

## 6. Доступність

При проєктуванні компонентів враховано базові вимоги **Web Accessibility (a11y)**.

### Реалізовані механізми

* доступне навігаційне меню через `aria-label`;
* зв'язування секцій із заголовками через `aria-labelledby`;
* наявність `.skip-link` для швидкого переходу до основного контенту;
* єдиний семантичний `<main id="main-content">`;
* правильне зв'язування `label` та `input` через `for` / `id`;
* використання `aria-describedby` для додаткових підказок;
* безпечне значення `type="button"` для кнопки за замовчуванням.

Таким чином, структура компонентів враховує не лише візуальне відображення, а й семантику HTML та доступність інтерфейсу.

---

## 7. Форма бронювання

`BookingFormPreview` є демонстраційним компонентом форми.

Він **не виконує фактичне надсилання даних**. Подія `submit` блокується за допомогою:

```jsx
e.preventDefault()
```

Для уникнення конфліктів `id` між полями використовується властивість:

```text
idPrefix
```

Наприклад:

```text
booking-name
booking-email
```

Це дозволяє безпечно розміщувати декілька екземплярів форми на одній сторінці.

---

## 8. Переваги запропонованої архітектури

Запропонована компонентна структура забезпечує:

* **модульність** — кожен компонент має чітку відповідальність;
* **повторне використання** — універсальні компоненти можуть застосовуватися в різних частинах UI;
* **низьку зв'язаність** — компоненти взаємодіють переважно через `props`;
* **зменшення дублювання** — спільна логіка винесена в окремі компоненти;
* **підтримуваність** — зміни в одному компоненті не потребують редагування всієї сторінки;
* **масштабованість** — структура готова до подальшого розширення функціональності;
* **доступність** — компоненти містять необхідні семантичні та ARIA-атрибути.

## 9. Перспективи подальшого розвитку

Поточна архітектура створює основу для наступних етапів розвитку застосунку.

У майбутньому можливе:

1. підключення **React Router** для повноцінної маршрутизації;
2. використання **Redux Toolkit** для глобального стану;
3. винесення роботи з API в окремий шар;
4. додавання реального механізму бронювання;
5. розширення моделі `Tour`;
6. додавання фільтрації та сортування каталогу;
7. створення додаткових сторінок та функціональних модулів.


## Керування станом та взаємодія компонентів

### 1. Карта стану та похідні значення

Усі дані та стани інтерфейсу декомпоновано за принципом єдиного джерела істини (Single Source of Truth) з чітким розмежуванням областей видимості.

| Назва стану / значення | Тип даних | Початковий стан | Власник стану | Споживачі (компоненти) | Дія скидання | Призначення |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `detailsOpen` | `boolean` | `false` | `TourCard` | `TourCard` | Демонтування картки / клік на «Приховати» | Локальне керування розгортанням повного опису туру |
| `query` | `string` | `""` | `useTourFilters` (`HomePage`) | `TourFilters` (інпут пошуку) | `resetFilters()` або стирання тексту | Збереження тексту пошукового запиту за назвою |
| `availableOnly` | `boolean` | `false` | `useTourFilters` (`HomePage`) | `TourFilters` (чекбокс) | `resetFilters()` або зняття позначки | Фільтрація турів лише з доступними місцями |
| `visibleItems` | `Array` | *Похідне значення* | Обчислюється у `useTourFilters` | `TourList`, лічильник у `HomePage` | Перераховується автоматично | Відфільтрований список турів без мутації вихідного масиву |
| `selectedId` | `string \| null` | `null` | `TourSelectionProvider` (Context) | `TourCard` (підсвітка), `BookingPage` | `clearSelection()` | Ідентифікатор туру, обраного для бронювання |
| `selectedTour` | `Object \| null` | *Похідне значення* | Обчислюється у `TourSelectionProvider` | `BookingPage`, `BookingSummary` | Автоматично стає `null` при `selectedId = null` | Повний об'єкт обраного туру, знайдений через `.find()` |
| `draft` | `Object` | `{ customerName: '', ... }` | `BookingPage` | `BookingForm`, `BookingSummary` | `handleReset()` або зміна `key` | Збереження чернетки контактних даних клієнта |

> **Примітка щодо похідних значень (Derived State):**  
> `visibleItems` та `selectedTour` навмисно не використовують `useState` або `useEffect`. Вони детерміновано вираховуються з базових даних (`items`, `selectedId`, `query`, `availableOnly`) під час кожного рендеру, що унеможливлює розсинхронізацію стану.

### 2. Засоби керування станом та обґрунтування вибору

| Потреба | Достатній засіб | Фактичний компонент / хук | Обґрунтування вибору для теми «Турагентство» |
| :--- | :--- | :--- | :--- |
| **Розгортання деталей туру** | Локальний `useState` | `TourCard` | Стан потрібен виключно одному екземпляру картки. Зміна стану однієї картки не повинна спричиняти перерендер сусідніх. |
| **Пошук і доступність у каталозі** | Власний хук, props | `useTourFilters` (`HomePage`) | Параметри потрібні виключно формі фільтрації та списку каталогу в межах одного сценарію. Відокремлює бізнес-логіку від UI. |
| **Видимі записи й лічильники** | Звичайні обчислення (Derived State) | Метод `.filter()` у `useTourFilters` | Похідні значення визначаються вихідним масивом і поточними фільтрами. Окремий стан призвів би до дублювання та помилок синхронізації. |
| **Поля та підсумок чернетки** | Підняття стану до спільного предка | `BookingPage` | Два сусідні компоненти (`BookingForm` та `BookingSummary`) повинні в реальному часі читати один і той самий об'єкт чернетки. |
| **Скидання форми при зміні туру** | Декларативний скид через `key` | `key={selectedId ?? "empty"}` | При зміні обраного туру React автоматично демонтує старий екземпляр `BookingPage` і монтує новий із чистим початковим `draft`, уникаючи сторонніх ефектів. |
| **Узгодження каталогу та бронювання** | Обмежений Context API | `TourSelectionContext`, `TourSelectionProvider` | Вибір туру узгоджує дві віддалені гілки робочої області (`CatalogContainer` та `BookingContainer`), усуваючи прокидання пропсів через `AppLayout`. |
| **Заголовок вкладки браузера** | Ефект `useEffect` | `BookingPage` | Синхронізація зі сторонньою властивістю браузера (`document.title`) із гарантованою функцією очищення (`cleanup`) при розмонтуванні. |

### 3. Контракти подій (Event Contracts)

Для взаємодії між компонентами визначено суворі контракти подій за принципом односпрямованого потоку даних (Data Down, Events Up):

1. **`onSelect(id)`**
   * **Відправник:** `TourCard` (кнопка вибору туру).
   * **Власник стану:** `TourSelectionProvider`.
   * **Зміна:** Викликає `selectTour(id)`, валідує існування туру через `items.some()` та оновлює `selectedId`.

2. **`onClearSelection()`**
   * **Відправник:** `BookingPage` (кнопка «Скасувати вибір туру»).
   * **Власник стану:** `TourSelectionProvider`.
   * **Зміна:** Викликає `clearSelection()`, встановлює `selectedId = null`, що повертає форму в стан `EmptyState`.

3. **`onQueryChange(text)`**
   * **Відправник:** `TourFilters` (поле пошуку).
   * **Власник стану:** `useTourFilters` (у `HomePage`).
   * **Зміна:** Оновлює рядок `query`, що ініціює перерахунок `visibleItems`.

4. **`onAvailableOnlyChange(flag)`**
   * **Відправник:** `TourFilters` (чекбокс доступності).
   * **Власник стану:** `useTourFilters` (у `HomePage`).
   * **Зміна:** Оновлює прапорець `availableOnly`, відсіюючи неактивні тури.

5. **`onReset()`**
   * **Відправник:** `TourFilters` (кнопка скидання фільтрів).
   * **Власник стану:** `useTourFilters` (у `HomePage`).
   * **Зміна:** Викликає `resetFilters()`, повертаючи `query = ""` та `availableOnly = false`.

6. **Події оновлення чернетки (`onCustomerNameChange`, `onPhoneChange`, `onEmailChange`, `onNotesChange`, `onNeedsTransferChange`)**
   * **Відправник:** `BookingForm` (відповідні інпути та текстові поля).
   * **Власник стану:** `BookingPage`.
   * **Зміна:** Викликають чисте оновлення через spread-оператор (наприклад, `setDraft(prev => ({ ...prev, customerName }))`), зберігаючи незмінність об'єкта. Оновлені дані миттєво відображаються у `BookingSummary`.

7. **`onDraftReset()`**
   * **Відправник:** `BookingForm` (кнопка очищення чернетки).
   * **Власник стану:** `BookingPage`.
   * **Зміна:** Скидає стан полів до фабричного об'єкта `createEmptyDraft()`, не скидаючи при цьому сам обраний тур.

### 4. Обґрунтування області застосування Context API

У проєкті застосовано **`TourSelectionContext`**, область якого свідомо обмежено робочою областю вибору та бронювання:

* **Межі провайдера:** `<TourSelectionProvider>` обгортає лише контейнери `CatalogContainer` та `BookingContainer` всередині `App.jsx`. Хедер, навігація та футер не входять у залежності провайдера, оскільки вони не використовують дані вибору.
* **Захист від надлишковості:** У контекст винесено **виключно** `selectedId`, `selectedTour`, `selectTour` та `clearSelection`. 
* **Локальні стани залишено локальними:**
  * Фільтри каталогу залишено в хуку `useTourFilters`, оскільки форма заявки не повинна перерендеритися під час введення тексту в пошук.
  * Чернетку клієнта (`draft`) залишено в `BookingPage`, оскільки картки каталогу не потребують відомостей про введений користувачем телефон або ім'я.
* **Безпека доступу:** Доступ реалізовано через захищений хук `useTourSelection()`, який викидає інформативну помилку (fail-fast), якщо компонент викликано поза межами провайдера.
